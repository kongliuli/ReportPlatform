**根因分析**：4 个风险共享两个根因——

1. **模型体系分裂**（R-001）：Contracts 层和 Generators 层各自维护一套元素模型，导致渲染逻辑无法共享（R-003），扩展时需同步修改两套模型（R-004）
2. **契约层不完整**（R-002）：Contracts 层定义了 `AdapterType` 枚举但缺少 `IDataAdapter` 接口，导致适配器无法多态管理，新增适配器必须修改 MainViewModel（R-004）

## 3. 风险详细摘要

### R-001：双重模型体系与 `new` 隐藏 🔴

**核心问题**：Generators 层的 `ReportExternalElementBase` 继承 Contracts 层的 `ExternalElementBase`，但使用 `new` 关键字隐藏了 14 个属性（将 nullable 改为 non-nullable），导致多态访问陷阱、序列化歧义和默认值不一致。

**最严重场景**：模板 JSON 在 Editor → Generators → Editor 的数据往返中，nullable 属性的 null 值被替换为非空默认值，造成数据语义丢失。

**推荐方案**：组合替代继承——将 `ReportExternalElementBase` 改为包含 `ExternalElementBase` 实例的组合类，消除 `new` 隐藏。

### R-002：适配器接口缺失与不统一 🟡

**核心问题**：三种适配器（Excel/Database/Context）没有实现共同的 `IDataAdapter` 接口，方法签名不一致（同步 vs 异步），功能支持程度差异大（校验/批量），无法多态管理。

**最严重场景**：新增适配器类型（如 API 适配器）时，开发者无契约指导，只能参照现有适配器自行设计，容易引入不一致的 API 风格。

**推荐方案**：在 Contracts 层定义 `IDataAdapter` 接口，三种适配器统一实现，同步方法包装为异步。

### R-003：PDF 渲染双重实现 🟡

**核心问题**：Editor.Core 的 `PdfTemplateRenderer`（427 行）和 Generators 的 `PdfExportService` + `PdfElementRenderer` 各自独立实现 PDF 渲染，输入模型不同，渲染结果可能不一致。

**最严重场景**：同一模板在编辑器预览和数据生产端导出的 PDF 存在视觉差异，用户无法确认最终输出效果。

**推荐方案**：提取共享渲染层，统一输入模型和渲染逻辑。依赖 R-001 修复。

### R-004：扩展性瓶颈 🟡

**核心问题**：MainViewModel 承担 6 种职责（God Object），新增适配器需修改该类；`ElementJsonConverter` 和 `ElementGroupRegistry` 使用静态注册表，新增元素类型需修改 5 个现有文件。

**最严重场景**：第三方无法通过插件方式扩展元素类型或适配器，限制了平台的生态扩展能力。

**推荐方案**：拆分 MainViewModel → 适配器插件化 → 元素类型动态注册（Attribute + 反射）。

## 6. 建议决策

### 立即行动

- **R-002**：在 Contracts 层定义 `IDataAdapter` 接口，三种适配器逐步实现。这是 ROI 最高的改进，不破坏现有代码，且为后续 R-004 的适配器插件化奠定基础。

### 规划中

- **R-003**：在 R-001 完成后提取共享渲染层
